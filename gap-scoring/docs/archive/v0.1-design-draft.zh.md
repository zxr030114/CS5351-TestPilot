## 1. 模块定位

```
GitHub PR
   │
   ▼
A  PR / Git Change Analyzer ──output.json──▶  B  Behavioral Change Detector
   │                                              │
   │                                              ▼
   └──────────────────────────────────────▶  C  Test Dependency Mapper
                                                  │
                                                  ▼
                                             D  Test Adequacy Analyzer
                                                  │  level 0-3
                                                  ▼
                                        ★ E  Test Gap Scoring & Explanation
                                                  │  gap_score + 人话解释
                                                  ▼
                                             F  GitHub PR Reporter
```

**E 的一句话职责**：把「这次改动有多危险」和「测试覆盖得有多到位」合成一个**可解释**的缺口分数，并给出人能看懂的结论。

### E 明确不做的事

| 不做 | 理由 |
| --- | --- |
| 重新解析 diff / AST | A 的 `output.json` 已经算好了实体、行号、类别、指纹 |
| 判断行为类型（branch / boundary / exception / return） | 是 B 的职责 |
| 查 `.testmondata` 或跑 coverage | 是 C 的职责 |
| 判断断言强度、给测试定级 | 是 D 的职责（见 §7 边界） |
| 自动生成测试代码 | 讨论里已明确排除：会让项目从 "Test Gap Detection" 漂移成 "AI Test Generator"，scope 失控 |

E 是**纯函数式的聚合层**：给定 (A, B, C, D) 的输出，产出分数和文字。这保证它可以离线单测，不依赖网络和数据库。

## 2. 输入契约

### 2.1 来自 A：`Change Importance`

取自 `output.json` 的 `changes[]`：

| 字段 | 用途 |
| --- | --- |
| `file_path` / `entity_name` / `line_start` / `line_end` | 唯一键 `entity_key = file_path::entity_name@line_start` |
| `change_type` | add / delete / modify / rename |
| `change_category` | Signature change / Logic change / Documentation change / Rename-Move |

建议权重（初始标定，可调）：

| change_category | Importance | 说明 |
| --- | --- | --- |
| `Signature change` | 1.00 | 接口变了，调用方可能直接崩 |
| `Logic change` | 0.90 | 行为几乎必变 |
| `add`（change_type） | 0.70 | 新代码没有历史基线，风险未知 |
| `delete`（change_type） | 0.60 | 调用方可能还在引用 |
| `Documentation change` | 0.00 | **直接跳过，不进打分**（A 已证明运行行为不变） |
| `rename` | 0.30 | 行为通常不变，只需迁移依赖键 |

### 2.2 来自 B：`Behavior Risk`

B 输出四类（第一版范围）：

| type | 含义 | Risk | 举例 |
| --- | --- | --- | --- |
| `EXCEPTION_BEHAVIOR_CHANGE` | 新增/改变了抛出的异常 | **1.00** | `return None` → `raise InvalidTokenError()` |
| `BOUNDARY_CHANGE` | 比较边界值变了 | 0.85 | `if age >= 18` → `if age >= 21` |
| `NEW_BRANCH` | 新增分支（含布尔条件） | 0.70 | 新增 `if user.is_blocked:` 分支 |
| `RETURN_BEHAVIOR_CHANGE` | 返回值形态变了 | 0.60 | `return amount` → `return round(amount, 2)` |

### 2.3 来自 C：`Test Reachability`

```json
{
  "entity_key": "src/payment.py::withdraw@30",
  "has_related_test": true,
  "executed_changed_lines": true,
  "affected_tests": [
    {"test_id": "tests/test_payment.py::test_normal_withdraw", "executed_ranges": [[30, 34]]},
    {"test_id": "tests/test_payment.py::test_insufficient_balance", "executed_ranges": [[35, 40]]}
  ],
  "mapping_source": "testmon_db"      // 或 "static_fallback"（冷启动）
}
```

`mapping_source` 直接影响 E 的置信度（见 §5）。

### 2.4 来自 D：`Adequacy Level`（★ 待 D 定稿）

讨论中确定的四级模型：

| Level | 含义 | Deficit |
| --- | --- | --- |
| `0` | No related test（没有任何相关测试） | 1.00 |
| `1` | Related test exists（有相关测试，但没执行到改动行为） | 0.85 |
| `2` | Test executes changed behavior（执行到了，但没有断言验证效果） | 0.70 |
| `3` | Test contains assertion related to changed effect（有针对性断言） | 0.00 |

> `Deficit = 1 - 保证度`。注意 Level 2 的 deficit 是 0.70 而不是 0.33 —— 因为"执行到但不验证"在实测里几乎等同于没测（断言缺失是最高频的假覆盖）。

## 3. 打分模型

### 3.1 公式

```
S1 = BehaviorRisk × ChangeImportance        # 结构风险（0-1）
S2 = AdequacyDeficit                        # 覆盖缺口（0-1）

Base    = 100 × (0.45 × S1 + 0.55 × S2)
Bonus   = Σ 命中的规则分（上限 15）
GapScore = min(100, Base + Bonus)
```

### 3.2 规则加成表（来自组内讨论）

| 触发条件 | 加分 | 说明 |
| --- | --- | --- |
| `No related test` | Base 已满分 | `S2 = 1.0`，无需额外加 |
| Relevant test but branch unexecuted | +4 | 有测试但没走到新分支 |
| Executed but no assertion | +3 | 走到了但没验证 |
| Boundary change without boundary test | +4 | 边界值改了却没人测边界 |
| Exception changed without `raises` test | +5 | 最危险的一类 |

### 3.3 已校验的样例：`src/payment.py::withdraw`

| 分量 | 取值 | 来源 |
| --- | --- | --- |
| BehaviorRisk | 1.00 | B：`EXCEPTION_BEHAVIOR_CHANGE`（`amount > balance` 现在抛 `InsufficientFunds`） |
| ChangeImportance | 0.90 | A：`Logic change` |
| AdequacyLevel | 2 | D：`test_insufficient_balance` 执行到了该分支，但没有 `assertRaises` |
| AdequacyDeficit | 0.70 | 由 Level 2 查表 |

```
Base  = 100 × (0.45 × 1.00 × 0.90 + 0.55 × 0.70)
      = 100 × (0.405 + 0.385)
      = 79.0
Bonus = 5（exception without raises）+ 3（executed but no assertion）= 8
GapScore = min(100, 79 + 8) = 87
```

→ **87 / 100，Risk: HIGH**，与讨论中的示例一致。

### 3.4 风险分档

| GapScore | Risk | 建议动作 |
| --- | --- | --- |
| ≥ 80 | `HIGH` | 阻断合并（F 用它做门禁），必须补测试或人工 review |
| 50 – 79 | `MEDIUM` | 提示，允许合并但需说明 |
| < 50 | `LOW` | 仅记录 |
| Level 3 且无规则命中 | `NONE` | 不出现在报告里 |

> 权重 `0.45 / 0.55`、`Deficit` 表、`Bonus` 上限都集中在**一个配置常量**里，实现时用 benchmark 数据校准，不改调用方代码。

## 4. 输出契约

```json
{
  "schema_version": "1.0",
  "module": "test_gap_scoring",
  "pr": {"repo": "owner/name", "number": 123, "head_sha": "abc1234"},
  "summary": {
    "changes_total": 12,
    "changes_scored": 7,
    "changes_skipped": 5,
    "gaps_high": 1, "gaps_medium": 2, "gaps_low": 4,
    "average_score": 41.3
  },
  "gaps": [
    {
      "entity_key": "src/payment.py::withdraw@30",
      "file_path": "src/payment.py",
      "entity_name": "withdraw",
      "entity_type": "function",
      "line_start": 30,
      "line_end": 46,

      "gap_score": 87,
      "risk": "HIGH",
      "confidence": "HIGH",

      "components": {
        "behavior_type": "EXCEPTION_BEHAVIOR_CHANGE",
        "behavior_risk": 1.0,
        "change_category": "Logic change",
        "change_importance": 0.9,
        "adequacy_level": 2,
        "adequacy_deficit": 0.7
      },
      "rule_hits": ["exception_without_raises_test", "executed_without_assertion"],

      "affected_tests": ["tests/test_payment.py::test_insufficient_balance"],

      "explanation": {
        "one_liner": "Exception branch is executed by a test, but nothing asserts InsufficientFunds.",
        "changed_behavior": "amount > balance now raises InsufficientFunds",
        "problem": "changed exception branch is executed, but no assertion verifies InsufficientFunds.",
        "suggested_test_input": "withdraw(balance=100, amount=101)",
        "evidence": [
          {"file_path": "src/payment.py", "line_start": 38, "line_end": 40, "kind": "changed_branch"},
          {"test_id": "tests/test_payment.py::test_insufficient_balance", "kind": "executed_no_assert"}
        ]
      }
    }
  ],
  "unscored": [
    {"file_path": "README.md", "reason": "noise: docs"},
    {"file_path": "src/legacy.py", "reason": "parse_failed"}
  ]
}
```

### 字段约定

- `entity_key` 用 `file_path::entity_name@line_start`，与 A/B/C/D 全程对齐（A 的 change 记录没有 `qualname`，同名嵌套方法靠行号区分）。
- `gaps` **按 `gap_score` 降序**，F 直接取前 N 条渲染 PR 评论。
- `unscored` 必须写清楚为什么没打分，禁止静默丢弃。
- `schema_version` 变动时下游（F）必须报错退出，不允许静默降级。

## 5. 置信度（Confidence）

| 条件 | Confidence |
| --- | --- |
| C 的 `mapping_source = testmon_db`，D 给出明确 Level，A 解析成功 | `HIGH` |
| C 用 `static_fallback`（冷启动、无历史 DB） | 降一级 |
| 该文件 AST 解析失败 / 被 `skipped` | **不出分**，进 `unscored` |
| D 的 level 缺失 | 视为 `Level 2` 并在报告里标注 `assumed` |

置信度的作用：`HIGH` 的 gap 才允许做合并门禁；`MEDIUM`/`LOW` 只做提示。

## 6. 解释文案规范

### 6.1 用词红线

| 禁止 | 必须 |
| --- | --- |
| "missing test" / "这个测试一定缺失" | **"Potential Test Gap"** / "可能的测试缺口" |

原因：静态 + 动态分析都有 false positive，自动断言"缺测试"会让人不信任工具。讨论里明确要求留有余地。

### 6.2 三段式模板

```
<file>::<entity> — Risk: <HIGH|MEDIUM|LOW>  (GapScore <n>/100)

Changed behavior : <B 的行为描述>
Affected tests   : <C 的测试列表，最多 3 个>
Problem          : <为什么现有测试不够 —— 必须指名是"没执行到"还是"执行到没断言">
Suggested input  : <一个具体的调用样例，不生成代码>
```

渲染示例（讨论中给出的目标形态）：

```
src/payment.py::withdraw — Risk: HIGH
Changed behavior : amount > balance now raises InsufficientFunds
Affected tests   : test_normal_withdraw, test_insufficient_balance
Problem          : changed exception branch is executed, but no assertion verifies InsufficientFunds.
Suggested input  : withdraw(balance=100, amount=101)
Test Gap Score   : 87/100
```

### 6.3 硬性要求

- 每条解释必须能追溯到 `evidence[]`（行号 / 测试名 / 断言），不能只有形容词。
- `suggested_test_input` 只写**参数和场景**，不写完整测试函数——避免滑向代码生成。
- 单条解释不超过 5 行，适配 PR 评论。

## 7. 与 D（Test Adequacy Analyzer）的边界 ★

这是当前唯一没定死的接口，也是两人协作最容易互相返工的地方。

### 7.1 责任划分

| 问题 | C 回答 | D 回答 | E 回答 |
| --- | --- | --- | --- |
| 这个测试碰过改动的代码吗？ | ✔ 覆盖行号 | — | 只消费 |
| 这个测试**验证**了改动的效果吗？ | — | ✔ Level 0-3 | 只消费 level |
| 断言强度怎么判？ | — | ✔ AST 断言抽取、`raises` 匹配 | 不看 AST |
| 缺口有多严重？ | — | — | ✔ 打分 |
| 缺口为什么严重？ | — | 提供证据片段 | ✔ 组织成人话 |
| 会不会误报？ | — | 提供 confidence | ✔ 汇总成最终 confidence |

**一句话边界：D 判"测没测到"，E 判"这个缺口有多要紧、怎么讲清楚"。**

### 7.2 建议的接口（需 D 确认）

```json
{
  "entity_key": "src/payment.py::withdraw@30",
  "test_id": "tests/test_payment.py::test_insufficient_balance",
  "level": 2,
  "evidence": {
    "assertions": [],
    "executed_lines": [[30, 40]],
    "matched_assertion_kind": null
  },
  "confidence": "HIGH"
}
```

### 7.3 必须和 D 谈定的 5 个问题

1. **Level 能不能由 E 复核？** 建议**不能**。一旦 E 自己再判一遍断言，就会有两套标准，测试对不上时无法归因。E 只消费。
2. **D 给不给 evidence？** 必须给。E 的 `problem` 字段需要"哪些断言被检查过"才能写出具体理由，否则只能写空话。
3. **粒度是 per (test, entity) 还是 per entity？** 必须是 **per (test, entity)** —— 一个实体常被多个测试覆盖，E 要挑"最强的那一个"来算 Level，并把其余的列进 `affected_tests`。
4. **多个测试并存时 E 怎么汇总？** 建议取 **max(level)**：只要有一个测试真的验证了行为，就算覆盖到位（最宽松，误报最少）。
5. **D 没完成时 E 能不能先动？** 能。E 先用 mock 的 level 跑通打分和报告（见 §9），D 交付后只替换数据源。

### 7.4 如果 D 迟迟不能交付

降级路径（不阻塞 E）：

- `Level` 一律按 `2`（执行到就算），E 仍能产出分数，只是 `HIGH` 会偏多；
- E 的报告里标注 `adequacy: assumed`，F 不把它当合并门禁。

## 8. 降配方案（Must / Should / Could）

对应讨论里给 6 人团队定的 Scope 分级：

| 级别 | 内容 | 说明 |
| --- | --- | --- |
| **Must** | 只用 C 的 `has_related_test` + A 的 `change_category`，输出二值判断 + 一句话解释 | 即使 B/D 都没好，E 也能独立交付 |
| **Should**（目标） | 完整公式（B × A × D）+ 规则加成 + 置信度 + JSON 报告 | 本文档描述的版本 |
| **Could** | Markdown/HTML 报告、可视化、LLM 生成解释 | 时间够再说 |

> 讨论原文把 "Test Gap Score / Confidence / PR comment / Dependency explanation / Suggested test input" 列为 **SHOULD**（"时间够再做"），把 Git diff、AST behavioral change、testmon affected tests、easy assertion analysis、Test Gap Report 列为 **MUST**。
> 也就是说：**E 的分数是加分项，不是及格线**。如果 sprint 时间紧，先保证 F 能出 Test Gap Report，E 退到 Must 版本。

## 10. 待解决的问题（TBD）

### 10.1 测试文件自身的改动算不算缺口？

实测 `pallets/flask#6168` 的 7 条 change 有 5 条在 `tests/` 下：

| 实体 | 文件 |
| --- | --- |
| `raise_any` | `src/flask/helpers.py` |
| `get_expiration_time` | `src/flask/sessions.py` |
| `test_robust_teardown` | `tests/test_appctx.py` |
| `test_session_expiration` | `tests/test_basic.py` |
| `test_session_special_types` | `tests/test_basic.py` |
| `test_config_from_file_toml` | `tests/test_config.py` |
| `test_dump_load_unchanged` | `tests/test_json_tag.py` |

**问题**：测试函数被修改，可能意味着断言被**削弱**（缺口变大），也可能只是**新增**（缺口变小）。A 只说"函数体变了"，判断不了方向。

**建议**：单独归类为 `test_quality_change`，**不计入 gap_score**，但输出一条提示：

> 该 PR 修改了 5 个测试函数，请人工确认断言未被削弱。

理由：把测试改动混进缺口分数会让分数失真（改测试反而"制造"缺口）。这条规则需要和 D 确认——判断"断言变强还是变弱"其实属于 D 的能力范围。

### 10.2 其他待定

1. `Bonus` 上限 15 是否合理？极端情况下（异常 + 无测试）会不会过早触顶？
2. `Risk` 分档线（80 / 50）要不要按项目调整？
3. F（GitHub Action）要不要把 `HIGH` 做成阻断门禁？这会影响团队日常效率，需全员同意。
4. 多语言（Java）场景下 B/D 的能力弱很多，E 是否要按语言降权？
