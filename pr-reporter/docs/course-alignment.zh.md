## 1. F 的范围

面向开发者的 PR 测试缺口反馈与评估模块。触发条件是代码 PR 或本地两个 Git 提交；输入是 A-E 报告，或可解析的完整项目历史；输出是可审阅的 JSON、Markdown、HTML 和评估结果。

提供单一主入口 `pr_reporter.py`，与 A-E 一样作为独立目录交付。为保持文件职责清楚，主入口使用四个实现文件；不是把所有逻辑塞进一个大文件。

## 4. 两个 NFR 与架构理由

### NFR-1：反馈可靠性及输入完整性

**指标：**定义的重复发布、输入缺失、错误报告、过期提交、跨文件同名函数、权限失败与门禁场景全部通过自动化验收；不修改输入仓库或原始数据库；数据未知不输出“测试充分”。

**架构方案：**将纯报告生成、A-E 编排与 GitHub REST 适配分开；采用稳定评论标记、目标仓库/PR/head 校验，版本快照隔离，并在 F 的连接适配器中使用完整行为身份。

**选择理由：**相比直接把 E 的 stdout 贴到 PR，上述方案使未知输入和运行错误有明确状态；相比每次创建评论，更新同一评论降低噪音；相比在用户工作区切换提交，临时克隆避免污染工作区。

**剩余限制：**检查 head 后到服务端写评论之间仍有很短的竞争窗口，GitHub issue-comment API 没有基于 PR head 的原子条件写入。workflow concurrency 和写入前二次查询只能缩小窗口。离线测试不证明 GitHub 服务本身可用。

### NFR-2：本地反馈性能

**指标：**固定验收数据的“读取 A-D + E 评分 + F Markdown/HTML 渲染”30 次采样（6 场景 × 5 次），p95 ≤ 2000 ms。该范围不包含 Git 克隆、pytest、网络或 GitHub API。

**架构方案：**本地评分复用现有模块、纯标准库报告渲染、不调用模型；评论只展示 Top-N 并限制正文长度；子进程设置超时。Git、基线测试与总流程另行计时。

**选择理由：**把可控本地耗时与环境相关的测试/网络耗时分开，避免把远程抖动误当成算法开销，也避免通过漏报慢阶段来宣传“整个流程毫秒完成”。

**验证证据：**运行 evaluate 后的 timing/checks；运行 demo 后 execution.timings_ms。机器、冷启动和真实项目规模会影响结果，不能外推为所有项目性能。

## 5. 风险登记与停止条件

| 风险 | 触发条件 | 可能性/影响 | 负责人角色 | 应对措施/停止条件 |
| --- | --- | --- | --- | --- |
| 假充分结论 | 没有测试源码、缺 C/D 或未评分变化 | 中/高 | F + D | 标注缺失与未评分；分析失败时不产出通过结论 |
| 历史基线不对应 | 外部数据库来自其他提交 | 中/高 | C + F | 外部 DB 必须声明 base SHA；记录为 caller_asserted，不能声称独立验证 |
| 源码版本陈旧 | 重用镜像或 PR 更新 | 中/高 | F | 全 SHA 独立临时克隆；发布前复核 head，不一致则停止 |
| 证据串用 | 多文件同名函数、相同行号 | 中/高 | E + F | F 连接器按完整行为身份取 D 记录；歧义时保留未知并降低证据可信度 |
| 不可信代码执行 | 将 PR head 代码作为带写权限脚本运行 | 中/高 | CI 负责人 | 分离只读分析和发布作业；head 只做静态解析；只运行 base 测试；fork 不自动发评论 |
| 基线测试依赖不完整 | 项目依赖额外插件、服务或不同运行命令 | 高/中 | 项目维护者 | 显式配置测试根和目标；基线失败则停止，不伪造空依赖库 |
| 样例过拟合 | 用六个样例宣称真实准确率 | 高/高 | 评估负责人 | 明确 synthetic；独立真实 PR 标注尚未完成，未知标签排除 |
| 课程过程证据不足 | 缺每周记录、三个 sprint、燃尽图 | 待团队确认/高 | 团队负责人 | 从实际发生时间维护，不补造历史记录；该代码不能替代过程要求 |
